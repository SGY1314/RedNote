## F1：旧输入生成的脚本会自动填入

复现步骤：

1. 在视频仿写中，以咖啡主题参考文案提交脚本生成。
2. 在该任务尚未完成时，将参考文案改成海边日落主题。
3. 原任务成功后，旧的咖啡脚本仍自动进入视频脚本框，没有提示它基于旧参考内容。

复现使用实际前端构建、桌面 Chrome 和模拟 API；没有请求真实模型。截图 `stale-script.png` 同时显示新参考文案和旧脚本。脚本填写逻辑只核对任务 request_id、成功状态和 applied_job_id，没有在应用结果时比较当前输入与提交时的输入指纹。参考内容在提交完成后仍可编辑。

源码位置：

- `web/src/rewrites/VideoScriptEditor.tsx:63`：成功结果自动写入脚本。
- `web/src/rewrites/VideoScriptEditor.tsx:82`：已有 requestKey/input_key，但目前主要用于复用提交请求。
- `web/src/rewrites/CreationWorkflow.tsx:893`：参考内容面板仅受 busy 控制，脚本在后台运行时仍能修改。

建议修改：将生成时的输入指纹与当前输入比较；一致时才自动填入。不一致时保留后台任务中的结果并显示简短的过期提示，避免自动覆盖。比较范围应包含实际参与请求的参考内容、提示词、补充要求、模型和时长。刷新后也应遵循相同判断。

建议验收：原参考不变时正常填入；运行中改参考、上游确认内容、提示词或时长时，不自动应用旧结果；旧任务结果仍保留；不会覆盖用户后续编辑。

## F2：重试旧任务时，主页面状态可能隐藏

复现步骤：

1. 同一项目有较早创建的失败任务 A，以及后来创建且成功的任务 B。
2. 在后台重试 A，后端将 A 改成 queued/running，保留原 created_at。
3. 前端按钮会因存在活动任务而禁用，但主区域仍按 created_at 选择 B，因此不显示 A 的进度。
4. A 再次失败时，B 仍排在最前面，A 的本次错误也不会显示在主区域。

桌面模拟 API 复现已确认执行中与再次失败两种状态；截图 `hidden-retry.png`，结果见 `desktop-findings.json`。

源码位置：

- `web/src/rewrites/MediaRewriteStep.tsx:183`：任务按 created_at 排序。
- `web/src/rewrites/MediaRewriteStep.tsx:190`：按钮检查所有相关任务是否活动。
- `web/src/rewrites/MediaRewriteStep.tsx:740`：反馈只取排序后的第一项。
- `web/src/rewrites/CreationWorkflow.tsx:921`：另一处阶段反馈也按 created_at 选择任务。
- `internal/app/jobs.go:266`：重试复用同一任务，更新状态和 updated_at，未改变 created_at。

建议修改：将“任务创建时间”和“本次执行开始时间”分开记录，页面按最近一次执行选择反馈，并优先显示当前活动任务。进度更新不能改变执行先后顺序。继续保留此前已修复的规则：后来一次执行成功后，更早失败不再出现在主区域。

建议验收：新建成功覆盖旧失败；重试旧任务显示运行状态；本次重试失败显示本次错误；重试成功清除旧错误；图片与视频反馈仍各自独立，后台历史保留。

## F3：手机交接上传阻塞其他项目保存

隔离复现：创建临时工作区、本地模拟交接服务和两个独立业务对象；在交接上传请求到达后暂停其网络响应，同时提交另一项目的标题草稿保存。保存请求在整个 700 毫秒观察窗口内未完成；释放上传响应后，交接返回 201，草稿保存随即返回 200。

这验证了阻塞关系；700 毫秒为复现中主动设置的观察窗口，不是实际最长阻塞时间。交接 HTTP 客户端的超时配置为 2 分钟，慢上传时等待可能显著加长。

源码位置：

- `internal/app/mobile_publish.go:60`：取得 a.mu，并 defer 到整个接口返回时释放。
- `internal/app/mobile_publish.go:92`：持锁制作发布快照。
- `internal/app/mobile_publish.go:104`：继续持锁等待文件上传。
- `internal/app/miniapp_cloud_client.go:86`：HTTP 超时为 2 分钟。
- `internal/app/creation_workflow.go:345`：草稿保存也要取得同一把锁。

建议修改：锁内校验并预留一次交接请求，固定稿件和素材快照；释放共用锁后执行文件处理和网络上传；完成后重新短暂加锁，核对请求标识再保存结果。保留现有防重复上传、稿件内容校验和未知结果处理，不能仅把锁删掉。

建议验收：慢上传期间另一个项目正常自动保存；同稿并发点击不重复上传；上传期间稿件替换、取消和上传响应丢失都有确定结果；失败不伪装成已发布。

证据：`handoff-lock-probe.log`，可复现探针源码副本 `project_audit_probe_test.go.txt`。探针只使用临时数据和本地测试服务，未访问真实云端。

## F4：发布组件测试与当前分支不一致

`publisher/upstream` 是独立 Go 模块，根目录 `go test ./...` 不包含它。本轮额外执行其 `go test -short ./...`，根包与 cookies 包有失败。

已确认的主要原因：

- `routes_test.go` 仍期待 MCP、通知等上游接口存在；当前 `routes.go` 和 `publisher/README.md` 明确只开放工作台需要的本地接口，已关闭这些入口。
- `cookies/cookies_test.go` 仍直接读取写出的会话为明文 JSON，并期待加载明文旧格式；当前实现通过 Windows DPAPI 加密保存。
- 临时目录回退测试使用 TMPDIR，但当前运行环境为 Windows，还需要对应平台的环境隔离。

工作台专用检查 `go test . ./cookies -run TestWorkbench -count=1` 通过。因此这里记录为测试维护问题，不能把这些失败直接当成当前扫码发布功能损坏，更不应为了让旧测试通过而重新开放已关闭的接口或退回明文凭据。

建议修改：更新旧断言以符合当前工作台契约，为保留的上游功能明确划定测试范围，并把嵌套 Go 模块加入统一检查入口。
